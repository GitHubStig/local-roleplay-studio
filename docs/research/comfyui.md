# ComfyUI as an image and voice backend: findings

What was learned adding ComfyUI beside mflux (from 2026-10-07; the decision in [ADR 0009](../adr/0009-comfyui-image-backend.md), voices in [ADR 0010](../adr/0010-voices-from-mlx-audio-or-comfyui.md)), on the owner's Mac and the Windows PC (RTX 4070, 12 GB; 16 GB of RAM). Kept to what still holds: the notes read against each release (0.39 to 0.42.5) are in the git history, and what they found that still matters is folded in here. Each Image Model's timings and pictures are in [image-models.md](image-models.md), and the current ones in [models.md](../models.md).

## Reading a new release

The repeatable upgrade and review procedure is in [comfyui-upgrade.md](../comfyui-upgrade.md); release-specific reviews live beside this note in [research/](.). This file keeps the continuing integration findings, not the current release's test log. A release-note entry is not evidence that an issue is fixed on either machine until it has been checked there.

When reviewing changes against what the app uses, look at:

- **The API:** `server.py` and `execution.py` (`/prompt`, `/view`, `/upload/image`, `/history`, `/interrupt`, `/free`, `/models`, `/object_info`, `/system_stats`, the WebSocket messages).
- **The workflows' nodes:** the inputs of every node in `server/images/comfyui/workflows/` and `server/voice/comfyui/workflows/`.
- **Tokenizer templates** of the encoders the app uses: 0.42 moved the empty think block (`<think>\n\n</think>`) out of the shared `Qwen3VLTokenizer` into each model's own; Qwen-Image 2.1 (and Turbo), FLUX.3 Klein and Z-Image Turbo get none, FLUX.2 Klein 4B gets the empty one.
- **comfy-aimdo**, the dynamic VRAM loader behind the one crash seen ("ComfyUI can crash and stay half-alive", below).
- **New models:** built-in ones are candidates for Image Models (below); partner (API) nodes are paid and send the picture off the machine, so they're not for the app.

## Comfy Desktop, ComfyUI, and who starts it

- **ComfyUI** is the engine: a Python program (`main.py`) that loads the models, runs workflows on the GPU, and serves its web interface and the API on a port (8188). It's what the app talks to.
- **Comfy Desktop** installs, updates (stable channel) and runs it. On the Mac it keeps the install in `~/ComfyUI-Installs/ComfyUI` and the models in `~/ComfyUI-Shared/models`, through a model-paths file it writes per install (`~/Library/Application Support/Comfy Desktop/instance-model-paths/inst-….yaml`); on the PC the install is in `%LOCALAPPDATA%\Comfy-Desktop\ComfyUI-Installs\ComfyUI`, its settings in `%APPDATA%\Comfy Desktop`. The portable build and a manual install run the same ComfyUI.
- **Two Pythons in a Comfy Desktop install.** `standalone-env/` is only the bootstrap (no torch); ComfyUI runs from `ComfyUI/.venv`, which also holds the workflow templates (`comfyui-workflow-templates-json`). Starting it by hand needs that one, and the model-paths file, or it sees only its own empty `models/`: `ComfyUI/.venv/bin/python main.py --listen 127.0.0.1 --port 8188 --extra-model-paths-config <the Desktop's file>`. It answers about 10 s after starting. Don't run it beside Desktop's on one port: a second ComfyUI on a taken port logs "Port 8188 is already in use" and exits, and whatever answers is the other one. Test instances go on 8189.
- **The app neither starts nor stops ComfyUI**: it expects one at the address in Settings (default `http://127.0.0.1:8188`; some Comfy Desktop builds used 8000) and says "Couldn't reach ComfyUI … is it running?" when none answers. Starting it from a command in Settings was dropped (ADR 0009, 2026-10-09).
- **Reaching the PC from the Mac** (for Upscale and pictures): ComfyUI must listen beyond `127.0.0.1`. Comfy Desktop has no listen setting; each installation has launch arguments (`installations.json`, `"launchArgs"`), where `--listen 0.0.0.0` goes, and Windows Firewall must allow TCP 8188 on the private network. ComfyUI has no login, so anything on the network can use it.
- **`localhost` is slow on Windows:** it tries IPv6 (`::1`) first, and a refused connection there takes time before IPv4 (2.1 s against 20 ms from PowerShell). The app's default is `127.0.0.1`.

## Through the API only

ComfyUI is the image backend on Windows (mflux is Mac only), so nothing in the client leans on either machine:

- **The API, never the file system.** ComfyUI may run on this machine or another, and its folders differ on each. `POST /prompt` queues a workflow in API format; the `/ws?clientId=…` WebSocket reports the running node and step progress and carries the pictures; `POST /upload/image` sends an input; `POST /interrupt` cancels, `POST /free` unloads models; `GET /object_info`, `GET /models/{folder}` and `GET /system_stats` list nodes, model files, the device and memory.
- **Model files differ per machine** (int8 on the Mac, maybe fp8 or GGUF elsewhere), so an Image Model on ComfyUI is a workflow plus a list of acceptable files per loader; the app takes the first that `GET /models/{folder}` lists, and says which is missing if none is. The workflow JSON never hard-codes one file.
- **Built-in nodes only**, so a fresh install runs every image workflow (voices are the exception: TTS Audio Suite, below).
- **The WebSocket carries everything, for every client:** messages are filtered by `prompt_id`. `progress` (`value`, `max`) also comes from non-sampler nodes, so only `max > 1` counts as steps. Binary messages are images: 4 bytes of type, then for type 1 a 4-byte format and the file. 0.40 added an optional `workflow_metadata` echo and a type 4 preview with a JSON header, sent only to a client that declares `supports_preview_metadata`; the app runs one prompt at a time, so it needn't.
- **Cancel only our prompt.** `POST /interrupt` with `{"prompt_id": …}` stops it only if it's the one running (without it, whatever is running stops, even another app's); `POST /queue` with `{"delete": [id]}` removes it if still queued.

## Keeping nothing on ComfyUI's side

The only copy of a picture is the one in the Session's folder. Checked on both machines: after a render, nothing in ComfyUI's output or temp folders, `GET /history` empty, no prompt text in its log ("got prompt" and timings only).

- **`SaveImageWebsocket`**, not `SaveImage` (which keeps a copy in `output/`) or `PreviewImage` (which writes to `temp/`, emptied only when ComfyUI starts). It's in ComfyUI's own repository (`custom_nodes/websocket_image_save.py`, so in every install) and sends the full-size PNG over the WebSocket to that client only.
- **The prompt is deleted from the history** (`POST /history` with `{"delete": [id]}`), which otherwise keeps the prompt text until a restart. ComfyUI writes the history only after it reports the prompt done (`main.py`'s `prompt_worker`: `execute()`, then `task_done()`, then `executing` with no node), and an interrupted prompt only once it has stopped; a delete sent earlier deletes nothing. So the client waits for the closing `executing` (up to 10 s) every time, after a Cancel too, before deleting.
- **Input pictures** (Upscale's) can't be sent inline with built-in nodes, and ComfyUI has no API to delete an upload. They go up with `type=temp`, are loaded as `"<name> [temp]"`, and after the job a 1×1 PNG is uploaded under the same name with `overwrite=true`, so only a 70-byte stub (a random `rpg-<uuid>.png`) waits in temp for ComfyUI's next start. A custom base64 loader would leave nothing, but every ComfyUI would need it.
- **Voices** have no WebSocket output node, so a clip ends in `PreviewAudio` (temp), fetched through `/view` and blanked the same way, its reference clip too.

## Memory and speed

- **Unload after every job.** ComfyUI keeps models loaded (~16 GB for Qwen-Image 2.1), and on a 12 GB card the Text Model can't load beside them: it spills to the CPU and replies slow many times over. So the client sends `POST /free` after each job and waits until ComfyUI's GPU is about as free as before the job (`/system_stats`, up to 30 s), as an mflux process frees its memory when it ends. The next picture pays the load again (~10 s on the PC, ~20 s on the Mac).
- **ComfyUI's own renders hold the GPU:** models from a render in ComfyUI's interface stay loaded, and the app frees them only after its own jobs. Once, 2.5 GB was free before the app started, and the Opening Frame's text took 80 s.
- **On the PC, ComfyUI loads and offloads a model and its encoder in turn** when they don't fit together (Qwen-Image 2.1's 6.8 + 8.7 GB int8, run as they come, no fp8 needed), fast enough: every Image Model so far fills the card at its peak (11.2–12.1 GB of 12.9 in use).
- **Mac against PC**, Qwen-Image 2.1 at 832×1216, 25 steps, seed 7, models loaded and freed each time (2026-10-07):

  | | Mac (M5 Pro, 48 GB): mflux | Mac: ComfyUI | PC (RTX 4070): ComfyUI, from the Mac |
  |---|---|---|---|
  | Picture, 8-bit / int8 | **96.5 s** (3.46 s a step) | **162.4 s** (5.86 s a step) | **20.9 s** (0.54 s a step) |
  | Picture, step cache 0.4 | **55.7 s** (1.97 s a step) | no step cache | no step cache |
  | Upscale, SeedVR2 7B to 2048×2992 | **66.4 s** | (needs Comfy-Org's files) | **14.0 s** |

  The PC's were run from the Mac over the network; on the PC itself 21–29 s and 12.4 s. So ComfyUI on the Mac is ~1.7× slower than mflux on the same model, and mflux stays the Mac's backend. Timings on the PC held within a second or two from 0.39 to 0.42.1.
- **Why the PC runs models bigger than its memory and the Mac doesn't** (2026-10-31, ComfyUI 0.43.2 on both; seen with MiniMax H3, whose int8 transformer is 20 GB and nvfp4 text encoder 15 GB, research/video-models.md). Read from ComfyUI's own log on each machine:
  - *The PC streams weights from disk.* Every model loads with `Model storage policy: fast_disk=True`: Dynamic VRAM (comfy-aimdo, CUDA only) maps the file rather than reading it into RAM, copies to the card only the layers being worked on, and drops them when the card fills, to read again from the SSD. A dropped layer costs nothing, so the text encoder and the transformer are never both in RAM: H3 ran a 5 s clip at 10.9 GB of VRAM and 14.2 GB of the 16 GB of RAM (much of that Windows' file cache). The price is reading from the SSD again each time, part of every clip's load time.
  - *The PC runs the compact formats natively*: `Native ops: asym_w4a8_int8, w6a8_int8, float8_e4m3fn, convrot_w4a4, int8_tensorwise, float8_e5m2`, only `nvfp4` and `mxfp8` emulated, so int8 and fp8 weights stay one byte each on the card.
  - *The Mac holds everything in memory, at a larger size.* `fast_disk=False`, and Dynamic VRAM is off ("No working comfy-aimdo install detected"), so each model is read whole into memory; `Native ops:` is empty, every quantized format emulated. Running H3, ComfyUI's process grew to 84 GB with 40 GB of files, likely the int8 weights widened to bf16 as they loaded (inferred from the sizes, not confirmed), and swap reached 29 GB before the first step.
  - *Unloading doesn't help on the Mac.* ComfyUI unloads a model by moving it to the CPU's memory, which on Apple silicon is the same memory; `--disable-smart-memory` (unload after use) and `--cache-none` made no difference, and `--fast-disk` does nothing without comfy-aimdo. The text encoder also stays referenced until the workflow ends ("0 models unloaded" when the transformer loads), and `POST /free` after an interrupt didn't give the memory back while swapping; it came back by itself later. Tried on a second ComfyUI on 8189, stopped by a watchdog once swap grew 4 GB.
  - *The way left on the Mac*, not tried: two workflows, the first encoding the prompt and pictures and saving them (`SaveConditioning`, `SaveLatent`), then `/free`, then the second loading them (`ConditioningLoader`, `LoadLatent`) with the transformer, so the encoder is gone before the transformer loads. Whether `SaveLatent` keeps what a video model's image-to-video node puts in its latent (which frames are held to the pictures) is unchecked.
- **Previews cost nothing:** asked for per prompt (`extra_data: { preview_method: "latent2rgb" }` on `POST /prompt`, as ComfyUI's frontend does), the sampler sends a half-size JPEG at every step, before the PNG; 21.7 s with them against 21.2–21.6 s without. `auto` and `taesd` give the same as `latent2rgb` for Qwen-Image 2.1 (there's no TAESD for its latent). They show the composition by step 5, soft and sharpening, never mflux's noisy static. The app shows them (design.md, "Image step").

## ComfyUI can crash and stay half-alive

Seen once (2026-10-07, 0.39.1, the PC): loading Qwen-Image 2.1's text encoder, ComfyUI logged `aimdo: … comfy-aimdo WDDM VRAM query failed. Using physical capacity as fallback`, then `Fatal Python error: Aborted` (in `model_patcher.load`). The process stayed, port open and the app's WebSocket connected, but answered nothing, so the render waited for good. Since then a running job asks `GET /system_stats` every 15 s and fails ("ComfyUI stopped answering (it may have crashed): restart it") after two checks with no answer; the calls sent without waiting (`/interrupt`, `/history`, `/free`) give up after 10 s, the upload after 60 s. Cancel still frees it at once. Why the memory query failed wasn't found. Fixes that may touch it: comfy-aimdo 0.5.6 in 0.40 (Qwen-Image 2.1 "rogues" offloading with little VRAM, [#16870](https://github.com/Comfy-Org/ComfyUI/pull/16870)) and a GPU sync before a CUDA graph is dropped in 0.42.1 ([#17178](https://github.com/Comfy-Org/ComfyUI/pull/17178)). It hasn't come back in the runs since, too few to say it's gone.

## Image Models built into ComfyUI

Each runs with built-in nodes only, from ComfyUI's own template, taken into a workflow in `server/images/comfyui/workflows/` ([image-models.md](image-models.md) has their timings and pictures):

- **Qwen-Image 2.1** (`image_qwen_image_2_1_t2i`): `UNETLoader`, `CLIPLoader` (Qwen3-VL 8B, type `qwen_image`, which ComfyUI recognises and gives Qwen-Image 2.1's tokenizer), `TextEncodeQwenImage21` (prompt, negative, and optional reference images at about 1024 px: the route for reference portraits and edits, as `--image-paths` is on mflux), `EmptyLatentImage` (adapted to the model's latent channels by `fix_empty_latent_channels`), `KSampler` 25 steps, CFG 1, euler, simple; sampling shift 0.69. The template's optional prompt rewriter (`TextGenerate`, a 9B Qwen 3.5) is off by default and left out; `QwenImage21Cache` defaults to `auto` and is left out too.
- **Edits** (ADR 0021; since 2026-10-24, reworked 2026-10-26), with built-in nodes, from ComfyUI's templates `image_qwen_image_2_1_image_edit` and `image_flux3_klein_distilled_image_edit`, each on its Image Model's files and steps (`COMFYUI_EDITORS`), without the templates' prompt rewriters: the picture through `LoadImage` as the reference (Qwen-Image 2.1: `TextEncodeQwenImage21` with the VAE and `resolution` 0, the picture's own size; FLUX.3: `ReferenceMultiLatent`, `keep resolution`, the picture being `<ref_image_0>` in the prompt); the painted area through `LoadImageMask` (red) and `SetLatentNoiseMask` over the picture's own latent (`VAEEncode`), so only it is repainted; then `ImageCompositeMasked` pastes the picture back around it. FLUX.3 is also told where by boxes: `CreateBoundingBoxes` and `Flux3LayoutPrompt` (0.42) append a JSON table of `{id: "obj_N", bbox: [ymin, xmin, ymax, xmax] in thousandths, desc}` to the prompt, cited as `<obj_N>`; the app writes the same table from the painted mask (`maskBoxes`, `prompts/images/flux3-edit.md`). Timings and what each change did are in [image-models.md](image-models.md#edits-through-comfyui-windows-pc).
- **FLUX.3 Image Klein** (0.41; `flux3-klein`): a 5.6B DiT on the FLUX.2 VAE with Qwen3-VL-4B (`CLIPLoader` type `flux3`). Gated (`black-forest-labs/flux-3-image-klein-comfy`, FLUX Kommunity License): `_sd_` files are the distilled checkpoint (16 steps, no guidance), the rest Klein Base (50 steps, CFG 3.5). The template runs a prompt upsampler first (a Qwen3.5 9B fine-tune) and BFL's card says not to go without one, as the model takes full scene captions; the app leaves it out, as the Text Model already writes the full scene and one Text Model does every text job. The full FLUX.3 is API only.
- **MOSS-Image** (0.42; `moss-image`), **Ming-Image** (`ming-image`), Qwen-Image 2.1 Turbo, FLUX.2 Klein 4B and Z-Image Turbo: [image-models.md](image-models.md).
- **FIBO 2.0** (added 2026-10-27): Dev and Edit Turbo have app workflows, and each was run once on the Windows PC; results are in [image-models.md](image-models.md#fibo-20-on-comfyui-2026-10-27-windows-pc). Turbo is also a generator (`fibo-2.0-turbo`, 2026-10-28: the Edit Turbo checkpoint in a text-to-image workflow, ~10 s against Dev's ~60 s; [image-models.md](image-models.md#fibo-20-on-comfyui-2026-10-27-windows-pc)). More prompts, seeds, bf16 weights and fit under concurrent Ollama load remain unchecked; the optional 2 GB Turbo LoRA was not tested.
- **Not used, maybe later:** `MOSSImageControl` (0.42.3, experimental: a colour-region map and a depth map through a control adapter loaded as a LoRA; nothing without one). Not for the 4070: FastH3 OmniRef (0.42.4, image to video with sound: 40 GB, and its 32B text encoder in nvfp4 needs a Blackwell card).

## Upscaling: SeedVR2

- **Built in** (since 0.39.1), with templates for 3B and 7B (`utility_seedvr2_{3b,7b}_int8_upscale_image`: `LoadImage` → `SeedVR2Preprocess` → `VAEEncodeTiled` → `SeedVR2Conditioning` → `KSampler` (one step, CFG 1) → `VAEDecodeTiled` → `SeedVR2PostProcessing`). It's the model mflux uses, so the Upscaler setting (7B or 3B) carries over. Comfy-Org's files (`Comfy-Org/SeedVR2`): int8 (listed first, so the Mac's build wins where both are) or fp8 (for an NVIDIA card), 7B ~8.2 GB, 3B ~3.4 GB, a 0.5 GB VAE; nvfp4 is for newer cards than the 4070.
- **mflux's SeedVR2 files don't load in ComfyUI** (numz's fp16 layout, for the SeedVR2 custom node: "Could not detect model type"), so on the Mac Upscale stays with mflux unless "Upscale with" sends it to a ComfyUI machine, which needs Comfy-Org's files.
- **On the PC** (fp8, 2026-10-07): 512×512 → 2048×2048 in 9.5 s (7B) and 7.9 s (3B); 832×1216 → 2048×2992 in 12.4 s and 11.1 s; about 5× the Mac. Most of it is the tiled VAE (40 tiles each way at 2048×2992, reported as the job's "steps"), so 3B saves little. Peak VRAM 9.6–9.8 GB (7B), 5.3–5.5 (3B).
- **Colour: `lab`, not the template's `none`**: with `none` the result came out 11% darker (red −17%); with `lab` (the node's own default) within 2%, the added detail the same.
- **Size:** "scale shorter dimension" to 2048 on `ResizeImageMaskNode`, as mflux's `--resolution 2048`; 832×1216 comes out at 2048×2992.
- **The Upscaler's own address:** Settings' `imageBaseUrl` at upscale time; a render uses its Session's. A Mac can keep mflux for pictures and send only Upscale to the PC.
- **Why the Mac's mflux upscale takes a minute:** one SeedVR2 step is ~15 s; the rest is loading 16.5 GB of fp16 weights in a new process every time, and the tiled VAE.

## mflux and ComfyUI side by side

- **A fixed seed reproduces a picture only within one backend.** The noise comes from a different generator (MLX, PyTorch), the schedules differ (mflux's "linear", ComfyUI's "simple" with its 0.69 shift), and the weights are quantized differently. Qwen-Image 2.1, seed 7: **different compositions**, mean pixel difference 23.5 of 255 (mflux with and without its step cache: 2.4). [bench/backends/seed7-mac.webp](../bench/backends/seed7-mac.webp).
- **The same seed on two ComfyUIs (Mac, PC) gives the same scene, not the same picture:** ComfyUI makes the noise on the CPU, so the layout matches; details part ways (difference 12.75), most likely int8 arithmetic differing between MPS and CUDA. [bench/backends/seed7-comfyui-mac-pc.webp](../bench/backends/seed7-comfyui-mac-pc.webp).
- **Within a Session it holds:** a Session keeps the backend and address it started with, so its re-renders don't change engine.
- **Upscale is all but the same:** both correct colour in LAB space; mflux kept brightness exactly, ComfyUI's came out 2% darker, mean difference 3.8, the added detail much the same. So one Session can hold upscales from both. [bench/backends/upscale-mflux-comfyui.webp](../bench/backends/upscale-mflux-comfyui.webp).
- **Alpha.** Qwen-Image 2.1's VAE decodes RGBA, and its alpha isn't a solid 255: it wavers between 240 and 255. TripoSplat's `preprocess_image` took that for a cut-out already made and skipped BiRefNet, making the whole picture into the "figure"; `python/triposplat/make.py` now hands it RGB. Qwen-Image 2.1's edit mode reads the fourth channel as an edit mask, so such a picture fed back as a reference could come back faintly see-through. **Since 2026-10-07 ComfyUI sends RGB:** the workflows split the alpha off before `SaveImageWebsocket` (`SplitImageWithAlpha`), 12–16% smaller files. Pictures made before are still RGBA.

## Voices through ComfyUI

The voice service is mlx-audio, Mac only; on the PC ComfyUI speaks instead (ADR 0010), through **TTS Audio Suite**, the one custom node pack the app needs. Nothing local is built into ComfyUI for TTS (only paid API nodes), though its core has the audio plumbing (`LoadAudio`, `SaveAudio`, `PreviewAudio`).

- **Why that pack:** it has both models the app uses, Qwen3-TTS VoiceDesign (`design`: a description to a reference clip) and Higgs Audio v3 (`speak`: cloning the clip for each line, with its transcript), and Higgs's own tags (`<|prosody:…|>`, `<|sfx:…|>`, `<|style:whispering|>`) pass through as the voice service writes them. The other packs had Qwen3-TTS only, or pinned transformers 4. Against it: its requirements pull in far more than two engines need, into ComfyUI's Python (Comfy Desktop's snapshots allow a rollback).
- **Installing, on the PC:**
  - Through the Manager, or with `ComfyUI\.venv\Scripts\python.exe`: a node's `install.py` run with the base Python sees no torch and installs a CPU torch there.
  - The Manager won't install while ComfyUI listens on the network (`--listen 0.0.0.0`): take it out of the launch arguments, install, put it back (or set `network_mode = personal_cloud` in `user\__manager\config.ini`, which lets anyone on the LAN install nodes).
  - Qwen3-TTS doesn't work on transformers 5, so the pack runs it in an isolated runtime (a venv inheriting ComfyUI's torch, with transformers 4.57.3, in `custom_nodes\tts_audio_suite\runtimes\shared_legacy_t4\`) as a worker process; Higgs v3 runs in ComfyUI's own. Building that runtime needs Windows' long paths on (`HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled` = 1, admin, then restart ComfyUI): pip hit a 270-character path.
  - The worker failed at once in 5.8.4 ("'utils' is not a package", [#366](https://github.com/diodiogod/TTS-Audio-Suite/issues/366)); fixed in 5.9.3, installed through the Manager as "nightly", as Comfy's registry flagged every release after 5.8.4 (open-threads.md). The worker's own errors are only in Comfy Desktop's log (`ComfyUI-Installs\ComfyUI\logs\comfyui.log`), not `ComfyUI\user\comfyui.log`.
  - Higgs v3 downloads on first use (8.9 GB) to the shared `models\TTS\higgs_audio_v3\`; Qwen3-TTS to the install's own `models\TTS\qwen3_tts\`.
- **The voice holds:** cloned lines' median pitch 102.5 Hz against the Mac's 106 on the same lines (reference 97); pace, sound and whisper tags work, none spoken as words. **But the whisper style alone pulls a voice up** through this pack (198–213 Hz against 81–102 without, unlike the Mac), so the ComfyUI backend whispers with `<|prosody:pitch_low|>` after it (70–77 Hz).
- **Slow:** Higgs speaks at ~9 tokens a second, ~3.7 s per second of speech (a median 5.5 s a line, against the Mac's 0.8 s per second of speech), wholly on the GPU, so it's the pack's decode loop; `eager` attention was no faster. A design takes ~30 s with the model loaded. Through the app, cold: a voice designed in ~73–75 s and a line in ~31–37 s, as ComfyUI unloads after every job; a Character's first line took 131 s from the click, with the Text Model unloaded and reloaded around each step.
- **Memory:** Higgs peaks at 9.9 GB of VRAM, so the Text Model must be out of the GPU first. `/free` releases it within ~8 s, and stops the VoiceDesign worker. TTS Audio Suite "unloads" Higgs by moving it to the CPU (~8 GB of ComfyUI's RAM, until a restart), which leaves the 16 GB PC tight.
- **Ollama crashed loading the Text Model** twice, right after a voice was designed, as ComfyUI stopped the VoiceDesign worker ("CUDA error: shared object initialization failed"; not VRAM, most likely the two processes' CUDA start and stop colliding). Ollama's chat now retries a model that died while loading once, after 3 s; a line spoken undirected says so beside Listen.
