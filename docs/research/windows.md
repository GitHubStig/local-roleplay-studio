# Windows, and backends other than Ollama and mflux (2026-10-06 to 2026-10-07)

The record of taking the app from a Mac only to Windows with an NVIDIA card: the plan and how each
step went, the first Windows run, the Text Model's context length on both machines, and the audit of
the AI services' interfaces that started it. Moved here from [open-threads.md](../open-threads.md)
on 2026-10-07, once done; what's left is there, under "Windows: what's left". ComfyUI's own
findings are in [comfyui.md](comfyui.md); SHARP, TripoSplat and LiTo on Windows in
[image-to-3d.md](image-to-3d.md).

## The plan, and how it went

- **Windows, and backends other than Ollama and mflux: the plan** (2026-10-06). The aim: the app runs on Windows (or any machine) with only Ollama installed, and each extra (images, voices, 3D) is on when its backend is there and off, hidden, when it isn't. Checked against the code on 2026-10-06, nothing run on Windows yet:
  - *What breaks on Windows today, with only Ollama.* The server, the web app and Ollama run; a Roleplay's conversation, Suggest and a Storyboard's plan work. **A Chain can't start**: its Opening Frame must render, and the default image backend is mflux (Mac only), so only `IMAGE_GENERATOR=placeholder` gets past it. Render and Upscale fail ("mflux-generate-… not found"); voices fail (mlx-audio, Mac only); SHARP and TripoSplat fail (their scripts use the Mac GPU, `mps`); LiTo fails (mlx-spatial, Mac only). Two plain bugs too: the first child process (any render, voice or 3D) throws, because `children.ts` listens for `SIGTERM` and Deno on Windows allows only `SIGINT` and `SIGBREAK`; and the uv scripts are passed as `new URL(…).pathname`, which is `/C:/…` on Windows (`fromFileUrl` is right).
  - *Order:*
    1. *(Done 2026-10-06; on Windows, child processes start without the `SIGTERM` throw (the SHARP and TripoSplat tests run one); the scripts' paths and `cuda` not run yet, as uv isn't installed.)* **Run on Windows without crashing:** signals by platform, `fromFileUrl` for the scripts, and each Python script picking `cuda`, `mps` or `cpu`, and on Windows and Linux fetching torch from PyTorch's CUDA index (PyPI's is CPU-only there; `uv tree --script … --python-platform x86_64-pc-windows-msvc` resolves `torch 2.11.0+cu128`). Small; worth it whatever follows.
    2. *(Done 2026-10-06, `server/features.ts`; confirmed on Windows with Ollama only: images, voices and LiTo off as Mac only, SHARP and TripoSplat off for want of uv; in Edge, the four Settings tabs show each with its reason, and the home page offers only a Roleplay.)* **What's available, decided at startup; Settings in tabs.** The server checks the platform, mflux on the PATH, uv, and the GPU, and reports each feature (images, voices, SHARP, TripoSplat, LiTo) as available or not, with why (`/api/settings/options` or `/api/health`). An unavailable feature is off and its buttons hidden (made audio, scenes and figures still play and open); available ones can be switched off in Settings. This replaces `VOICES`, `SCENES`, `FIGURES` and `LITO=off`. Settings grows tabs: **Text** (model, Thinking, Art Agent, Limits), **Images** (backend, model, size, steps, and mflux's Quantize, Step cache and Fast), **Voice**, **3D**. About two days.
    3. *(Done 2026-10-06, `server/text/`, [ADR 0008](../adr/0008-own-text-client.md); run against Ollama's `/v1` on the Mac and on Windows, not yet against LM Studio, llama.cpp or a cloud service.)* **An OpenAI-compatible Text backend** beside Ollama, for LM Studio, llama.cpp's server, and cloud services (OpenAI, OpenRouter): `/v1/chat/completions` with `response_format: json_schema`, `/v1/models`, a base URL and an API key in Settings. Today the text goes through Ollama's own API for its JSON-schema `format`, `think`, `/api/tags` and `/api/show`, and `keep_alive: 0`; the rest of the app only sees `TextModel` and `RoleplayModel`. Watch: structured output varies by provider and model, and every reply depends on it; Thinking is exposed differently by each; there's nothing to unload for a cloud model; and a cloud service applies its own content rules, so a dark Roleplay the local heretic plays may be refused. About a day.
    4. *(Built 2026-10-07 on the `feat/comfyui` branch, [ADR 0009](../adr/0009-comfyui-image-backend.md), findings in [research/comfyui.md](comfyui.md); run on the Mac, and on Windows on 2026-10-07: an RTX 4070 renders Qwen-Image 2.1 at 832×1216 in 21–29 s, 0.46 s a step. Upscale on ComfyUI added the same day, with its own "Upscale with" setting, so a Mac can upscale on the PC: SeedVR2 7B 512→2048 in 9.5 s against ~46 s with mflux; and from the Mac across the network to the PC, which the owner confirmed works (2026-10-07; ComfyUI started with `--listen 0.0.0.0` in Comfy Desktop's launch arguments for that installation, port 8188 allowed in Windows Firewall); the Mac's timing over the network not measured.)* **ComfyUI as an image backend** (below): about 2–3 days, plus a workflow per model.
    5. **Voices in the browser**, as an option on the Voice tab: the Web Speech API (no install, the system's voices, only pitch and rate) or a small model through transformers.js on WebGPU (Kokoro, 82M, preset voices; size and quality to check). Neither designs a voice from a description or clones one, as the voice service does, so a Character would pick a preset (gap 4 of the audit below). The web app would speak the line itself, with nothing on the server.
  - *3D on Windows:* **SHARP** yes: run on the RTX 4070 on 2026-10-07, ~31 s a scene through the app, peaking at 11.9 GB of the card's 12.3 (research/image-to-3d.md). **TripoSplat** yes: run on the RTX 4070 on 2026-10-07, ~52 s a figure through the app (faster than the Mac's 70-100 s), peaking at 6.5 GB, once ComfyUI's not-quite-opaque alpha stopped skipping its cut-out (research/image-to-3d.md). **LiTo** not as run here (mlx-spatial is an MLX port). *Checked 2026-10-07:* Apple did publish runnable code and weights ([apple/ml-lito](https://github.com/apple/ml-lito), ICLR 2026; weights from `ml-site.cdn-apple.com`, under `LICENSE_MODEL`), but its `pyproject.toml` declares only `linux-64` (NVIDIA, verified on A100, H100, B200, built for those chips only) and `osx-arm64` (the image-to-3D demo, on MLX); Windows isn't listed, and the Linux setup compiles nvdiffrast, spconv, TRELLIS (a submodule), xformers or flash-attention, gsplat and torchsparse. So on Windows it would mean WSL2 (not installed on the PC): either mlx-spatial's port on MLX's CUDA backend (light, the Mac's code path, unverified that its LiTo runs there) or Apple's PyTorch code (tens of GB and long builds; whether it fits 12 GB unknown), and the app running it through `wsl`. Parked: TripoSplat already makes figures on Windows.
  - *Testing:* steps 1 and 2 can be written and unit-tested on the Mac, but need a run on a Windows machine with an NVIDIA card to confirm; sessions, `settings.json` and the saved models aren't in git, so a fresh clone starts empty.
  - *First run on Windows* (2026-10-06; Windows 11, RTX 4070 12 GB, Ollama 0.35.1, Deno 2.9.7, no uv or mflux). `deno task test` failed 13 server tests, all in the tests rather than the app: stand-ins written as shell scripts (`sh -c`, `#!/bin/sh`, `pkill`), a `/`-joined path, and the API key file's `0o600` (Windows has no Unix modes). The SHARP, TripoSplat and voice stand-ins are Deno now; the five mflux ones are skipped on Windows, as mflux is Mac only. The Text Model here is Gemma 4 12B Heretic, the GGUF build (`hf.co/igorls/gemma-4-12B-it-heretic-GGUF:Q4_K_M`, 7.4 GB; measured 2026-10-07 on Ollama 0.40.0): a Roleplay through the API ran Cast, begin, two Messages and Suggest. Findings:
    - **Ollama's context length, and what it costs.** The app doesn't set `num_ctx`, and Ollama's Windows app had its context slider at 128k (`OLLAMA_CONTEXT_LENGTH=131072`, though its VRAM-based default here is 4096). Ollama reserves a GGUF model's context memory at load, so a model whose cache grows with the whole context can be pushed off the 12 GB card at 128k. Gemma 4 keeps most layers' cache to a short window, so it doesn't: at `num_ctx` 16k, 32k, 64k and 128k alike it loads at 7.5–8.3 GB, 100% GPU, and writes ~53 tokens/s. A 56,534-token chat at 128k was read in 30 s (~1,900 tokens/s), replied at 43 tokens/s with 11.2 GB of the card in use, and recalled the name and the code word from its first two messages. Having the app set `num_ctx` itself was considered and set aside: the slider stays, and the README says what to set (see "Ollama's context length on the Mac" below).
    - *Roleplay timings at 16k:* Cast 18.4 s (with the load), Replies 4.8–5.5 s, Suggest 2.2 s; in character, and never acting for the player.
    - *The OpenAI-compatible backend* ran the same Roleplay against Ollama's `/v1` at 16k: Cast 7.5 s, Replies 5.1–5.9 s, Suggest 3.8 s, all clean. As designed, its model list is everything `/v1/models` gives (here also `qwen3-vl` and the classifier `tev1`), each offered Thinking. The context comes from Ollama's slider, as the OpenAI API can't set `num_ctx`.
- **Ollama's context length on the Mac** (2026-10-06; measured on the Mac the same day, Ollama 0.35.1, below the plan). Decided: keep Ollama's slider rather than have the app send `num_ctx` (the OpenAI-compatible backend couldn't set it anyway); the README says what to set. The Mac's slider is at 128k. This app's Roleplays run up to 200 Frames. Estimate, not measured: ~2k tokens for the system message and Cast, then ~120–250 an exchange, so a 200-Frame Roleplay is ~25–50k. To measure:
  1. The longest Roleplay's prompt: send `roleplayMessages(session, 'x')` (`server/roleplay/prompt.ts`) for the longest Roleplay in `sessions/` to Ollama's `/api/chat` with the heretic, `num_predict: 1` and `num_ctx` 131072, and read `prompt_eval_count`.
  2. What the context costs on Gemma 4: `ollama ps` (SIZE) after a Reply with the slider at 32k, 64k and 128k. Most of Gemma's layers may cache only a sliding window, which would make a long context cheap; not checked.
  3. Pick the smallest value above the longest prompt and pi's sessions, weighed against "Memory headroom on a 48 GB Mac" above.

  *Measured (2026-10-06, M-series 48 GB):*
  1. The longest Roleplays' prompts, from `prompt_eval_count`: `07ac` (30 Frames) 8,126 tokens, `e211` (31 Frames) 10,697, `b215` (13 Frames) 3,368. The system message, Cast and opening are 0.7–1.5k; each exchange adds 220–314 tokens (above the estimate). So a 200-Frame Roleplay is ~45–65k.
  2. **On the MLX engine the slider doesn't matter.** `gemma-4-26b-heretic:nvfp4` (safetensors, so Ollama's MLX engine) loads at 17 GB, 100% GPU, at `num_ctx` 8k, 16k, 32k, 64k and 128k alike: the cache isn't reserved at load. It grows with the prompt instead: 18.3 GB at 10.7k tokens, 19.4 at 20k, 20.9 at 39k, 23.1 at 67k (~85 MB per 1k tokens; Gemma's sliding-window layers keep it small). Reading a 67k prompt from scratch took 32 s; a Reply normally reads only the new exchange, the rest being cached. And the MLX engine **doesn't enforce `num_ctx`**: at 4096 it still read a 26,466-token chat whole and answered from both ends of it.
  3. **On the GGUF engine (Windows, Linux, and GGUF models on the Mac), an overlong chat breaks the Reply.** With `qwen3-vl:4b` at `num_ctx` 8192 and a 26.5k-token chat, Ollama kept the system message (the model knew the code word in it), dropped the oldest exchanges (it lost the name given in the first one, and thought the chat began at turn 29), and filled the context to 8,002 tokens, leaving the reply 190: cut off (`done_reason: length`). So the app fails the Reply ("ran past its length limit") rather than the Character quietly forgetting the start.

  *So:* on the Mac, a slider at 128k costs this app nothing. On Windows, 16k fits a ~45–60-Frame Roleplay before Replies start failing. Two follow-ups. *Done 2026-10-06:* a reply Ollama cuts off short of its own token cap means the context ran out, so it fails with `ContextFullError` ("The conversation no longer fits the Text Model's context (8192 tokens). Raise the context length where the model runs…") instead of the length error, and isn't retried (`server/text/ollama/ollama.ts`, `withRetry`); checked against `qwen3-vl:4b` at `num_ctx` 8192 with an overlong chat. The OpenAI-compatible backend does the same from the counts `stream_options.include_usage` adds in a last chunk (dropped, like the other extras, if a server refuses it), shared in `lengthError` (`server/text/chat.ts`); checked against the same model on Ollama's `/v1`, which reports 226 of 400 reply tokens for the overlong chat and 20 of 20 for a reply cut at its cap. Not checked on LM Studio or llama.cpp. *Not done:* a long Roleplay on a small context would need its oldest exchanges summarised or dropped by the app itself, keeping the opening.

  On Windows (RTX 4070, 12 GB) the slider was at 16k, which by the measured 220–314 tokens an exchange no longer fits a Roleplay past ~45–60 Frames (its Replies then fail, point 3 above). With Gemma 4 12B Heretic (GGUF) that limit isn't needed: it stays 100% on the GPU up to 128k (2026-10-07, above). The slider is at 32k since 2026-10-07: ~100–140 Frames; 64k would cover a 200-Frame Roleplay.

## ComfyUI as a backend: the idea, before it was built (2026-10-02)

Built 2026-10-07 ([ADR 0009](../adr/0009-comfyui-image-backend.md)); the API as found then.

- **ComfyUI as a backend, for Windows with an NVIDIA card.** mflux is Apple Silicon only, so the app as built renders only on a Mac. ComfyUI runs on both, and has a local HTTP and WebSocket API (checked 2026-10-02 against the installed ComfyUI 0.37.4, Comfy Desktop, on `127.0.0.1:8188`):
  - `POST /prompt` queues a workflow (its "Export (API)" JSON) and returns a `prompt_id`;
  - `GET /history/{prompt_id}` or `/api/jobs/{id}` lists its outputs, and `GET /view?filename=…&type=output` fetches one;
  - `POST /upload/image` sends an input picture (for Upscale, edits, a panorama, TripoSplat);
  - the `/ws?clientId=…` WebSocket reports which node is running and step progress;
  - `POST /interrupt` and `/api/jobs/{id}/cancel` cancel, and `POST /free` unloads its models (useful before a voice or a scene, as for the Text Model);
  - `GET /object_info` lists installed nodes, and `/system_stats` GPU memory.

  It would slot in behind `ImageGenerator` as a third generator beside mflux and the placeholder: one workflow template per Image Model (and the upscaler), with the prompt, seed, steps and size filled in, chosen in Settings. Unlike mflux's process per image (ADR 0004), ComfyUI is a long-running server that keeps models loaded: faster renders, but it holds the memory until `/free`. What wouldn't come along on Windows: the voice service (mlx-audio is MLX, Mac only: Higgs TTS 3 and Qwen3-TTS have PyTorch releases that run on CUDA, or a ComfyUI TTS node), SHARP's script (hardcoded to `mps`; it runs on CUDA too, by changing the device), and the saved quantized copies (mflux's format; ComfyUI has its own fp8 and GGUF models). Ollama runs on Windows as is.

## AI services behind interfaces: the audit (2026-10-02)

Gaps 1, 2, 3 and 5 are done; gap 4 (voices assume a cloning TTS) is in open-threads.

- **AI services behind interfaces: five gaps** (audited 2026-10-02, with Windows and other providers in mind). The web app is cleanly separate: it imports nothing from the server and no Deno APIs, and talks to it only through `web/src/api.ts` (three `fetch` call sites, JSON and SSE) at `/api/…`, which Vite proxies to :8787, so any backend serving the same routes works. On the server, every service is an interface chosen once in `main.ts` (`AppDeps`): `TextModel` and `RoleplayModel` (Ollama), `ImageGenerator` (mflux, or SVG placeholders), `VoiceEngine` (the mlx-audio service), `SceneMaker` (SHARP), `FigureMaker` (TripoSplat, LiTo), and the stores (`SessionStore`, `SettingsStore`, `ScenarioLibrary`, `QuantizedStore`). Swapping a TTS means a new `VoiceEngine` and one line in `main.ts`. The gaps:
  1. *(Done 2026-10-07: each backend has its own list, `server/images/imageModels.ts`.)* *The image model list is mflux's and used everywhere.* `images/imageModels.ts` holds mflux commands and model ids; Settings validation (`settings.ts`), the `/api/settings/options` menu, steps, Quantize (mflux's saved 8-bit copies) and the Upscaler (SeedVR2) all read it. A ComfyUI or other backend would bring its own list: the `ImageGenerator` should advertise its models, sizes and options, and Settings validate against that.
  2. *(Done 2026-10-06: `server/text/chat.ts`.)* *The chat message type is Ollama's.* `ChatMessage` lives in `ollamaChat.ts`, and `roleplay/prompt.ts`, `art.ts`, `voice.ts`, `suggest.ts` and `testing.ts` import it from there. Move it to a neutral module.
  3. *(Done 2026-10-06: `main.ts` injects it, from the Session's Text backend.)* *`app.ts` defaults to Ollama itself:* `roleplayModel` falls back to `ollamaRoleplayModel` inside `createHandler` instead of being injected from `main.ts` like the rest, and `TextModelInfo` comes from `ollama.ts`.
  4. *Voices assume a cloning TTS.* `VoiceEngine` is `design` (a voice from a description) plus `speak` (cloning the designed reference clip), with pace, sound and whisper; a provider without cloning (preset voices only) would need another way to keep a Character's voice consistent, e.g. picking a preset once per Character.
  5. *The Python scripts are hard-coded to the Mac GPU (`mps`):* `python/sharp/make.py` (SHARP), `python/triposplat/make.py` (TripoSplat) and `python/lito/make.py`'s cut-out. They'd take a device (or detect CUDA) on Windows; LiTo runs only on MLX (Apple Silicon) at all.
