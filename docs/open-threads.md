- **App-managed ComfyUI model downloads** (investigated 2026-10-26). ComfyUI's core API lists files already installed in its model folders but has no generic model-download endpoint ([server API](https://github.com/Comfy-Org/ComfyUI/blob/master/server.py)); ComfyUI-Manager offers an optional Install Models catalog, with its own security settings ([Manager](https://github.com/Comfy-Org/ComfyUI-Manager#how-to-use)). Keep model installation separate for now; revisit if the extra machinery is worth it.

- **Reference portraits for Subject consistency** (rethought 2026-10-06 for mflux 0.21; split from picture edits 2026-10-22). The people in a Roleplay or Storyboard drift between Frames (a new seed, a new face), and the Look's words can only hold them so far. The idea: a portrait of each person, made once from the Look, passed with every render ("image 1 is Kael, image 2 is Elara Vance", then the Image Prompt). Each picture is still composed from its prompt, so the story leads and ADR 0005 holds (the Image Prompt is the state); the portraits only hold faces, hair and build steady. mflux 0.21's `mflux-generate-qwen-2.1-edit` runs Qwen-Image 2.1 with up to ten reference images, the references' attention cached across steps (`--use-kv-cache`, on by default); Viggle's turbo LoRA does it with 1–3 references in 6 steps. *Inputs must be RGB* (noted 2026-10-07): Qwen-Image 2.1's fourth channel is an edit mask, and a transparent input stays transparent, so a reference with alpha would come back see-through where it isn't opaque. ComfyUI's pictures were RGBA with alpha at 240–255 until 2026-10-07 (research/comfyui.md, "Alpha"), and older ones in Sessions still are: convert them to RGB first. The one deliberate exception is a cut-out on transparency (BiRefNet), e.g. a person alone as a reference. *Tried 2026-10-06* ([bench/reference-portraits](bench/reference-portraits/README.md)): portraits of Kael and Elara from the Kael tavern Roleplay's Look, then Frames 6, 9 and 12 without and with them. **The portraits hold identity well**: without them Elara is two different women in 9 and 12 and Kael's face changes in 12; with them both match their portraits in every Frame, and the two people stay apart. Costs: 1.4–1.7× the time (122–142 s against 84–86 s at 1024², Mac, some of it likely the edit tool's guidance), the same ~39 GB peak, the full 33 GB weights (the saved 8-bit copy can't take references), and the references pulling against the prompt (wider shots, smaller people; Frame 12 lost Elara's knives). Next: whether prompt wording or guidance fixes the composition, then portraits made once per Roleplay and passed with every render (Qwen-Image 2.1 only). Slots in behind `ImageGenerator`. *Another way, from mflux 0.23* (noted 2026-10-17): `mflux-generate-flux3-edit` runs FLUX.3 Klein (an Image Model since 2026-10-17) with up to ten reference images, in 16 steps, and takes `-q 8` (Qwen-Image 2.1's saved 8-bit copy can't take references). Smaller than Qwen-Image 2.1 (a 5.6B transformer, ~20 GB against 33 GB); mflux's README: an edit is described as a full caption of the result, not an instruction. Not tried: whether its portraits hold identity as well as Qwen-Image 2.1's did, or its speed with references. Nor whether ComfyUI (the PC) can pass references with either model. *When someone's looks change* (noted 2026-10-22): a portrait holds a face against the prompt, so after "I turn into a demon" it would pull the picture back towards the old face. But a Roleplay's pictures already keep the old looks, since the Look is copied word for word into every one ("Bringing a Roleplay's Look up to date with the story", below): portraits make that problem stronger, not new. So a portrait belongs to the Look: made again when the Look is edited (one render), and dropped from a Frame whose prompt changes that person's looks for a while (a disguise, a mask, a one-scene transformation). Re-rendering a Frame from before the change would get the new portrait, as it gets the new Look today.

- **Qwen-Image 2.1 ControlNet for composition** (noted 2026-10-09, mflux 0.22). `mflux-generate-qwen-2.1-controlnet` runs Alibaba's Fun ControlNet Union on Qwen-Image 2.1: a control picture at the target framing (canny, depth, grayscale, HED, lineart, MLSD, pose or scribble; one checkpoint reads all of them, no type flag) and `--controlnet-strength` (1.0 the strongest, 0 off), plus inpainting with `--image-path` and `--mask-image` (white is repainted from the prompt, black kept). mflux takes the control picture ready-made, so the app would have to make it (a depth map from Depth Pro, which mflux ships for `mflux-save-depth`; a pose from a pose model). - **Idle animation between Frames.** Keep the image alive while the player is thinking: flickering candles, drifting haze, the Subject blinking or shifting her weight, with the Image Prompt itself unchanged. Idle work must never block a Frame: it runs only after a commit, and is cancelled the moment the player sends an Action, since it competes for the same GPU and memory. Options, cheapest first:
  1. *Browser-only effects.* A slow pan and zoom over the still, plus ambient overlays picked from Image Prompt keywords (haze gives drifting fog, candles give a warm flicker, a rim light gives a soft pulse). Instant, and no extra rendering. Effects can't know *where* the candles are, so they stay generic.
  2. *Subject mask plus layered effects.* Cut the Subject out of the finished image with a background-removal model (mflux lists `fibo-edit-rmbg`; not downloaded yet, unverified), then animate only the background layer (fog, flicker, slight parallax) behind her. Better than rendering the background and Subject separately and compositing: separate renders don't share lighting, shadows or perspective, so the Subject looks pasted on.
  3. *Idle variant frames via image editing.* After commit, edit the Frame's image into a few near-identical frames ("eyes closed", "weight on the other foot", "candle flames taller") and crossfade or flash between them; a 150 ms eyes-closed frame every few seconds reads as a blink. Instruction-based editors in mflux 0.20: `mflux-generate-flux2-edit` (FLUX.2 Klein; weights already cached, likely ~15 s per frame), `mflux-generate-qwen-edit` (Qwen Image Edit, ~20B, not downloaded, much slower), `mflux-generate-kontext`, and `mflux-generate-fibo-edit`, which takes a `--mask-path` to edit only the background. The engine, not the player, writes these edit instructions, from a fixed list, so they stay within the Shoot Brief. *Revisited 2026-10-06 for mflux 0.21:* `mflux-generate-qwen-2.1-edit --auto-mask "his eyes"` finds a region from a description (its Qwen3-VL) and repaints only that ("his eyes closed"); pasting just that region back onto the original through a feathered mask keeps every other pixel exact (a whole-picture edit re-encodes it, and the swap would shimmer). Good for brief swaps (a blink, a flicker, a glance); not for motion (two poses crossfaded double-expose, so options 1 and 2 stay better for that). Each variant is a full edit render (unmeasured, likely a minute or more at 1024²) on the full Qwen-Image 2.1 weights (33 GB; the saved 8-bit copy can't edit), and renders unload the Text Model first, so variants made while the player types would make the next Reply reload it: make them after a pause, or when the picture viewer opens. *Tried 2026-10-06* ([bench/reference-portraits](bench/reference-portraits/README.md)): the composite works (99.75% of pixels byte-identical, only a box around the eyes touched), but the blink didn't (Elara's eyes stayed open; 0.01% of pixels moved). Retried the same day with demos ([bench/idle-animation](bench/idle-animation/README.md), in 2D and in SHARP's 3D): a hand-drawn eye mask and "eyelids fully closed" (not "blink") work; shown half, closed, half, the blink looks natural, and so does a crossfade, but a flashed "closed" alone is cartoony. The owner's picks: a calm flat glow on the lamps by default; **the painted light (an edit of the lamp flaring, faded in and out) is the standout**; a 2D flame wobble; depth glow too much indoors; painted flame shapes too much. All of it held up in 3D (glow as a light in the room, the edits as colour fades on the same splats), apart from the wobble there. For the app, the open problems are finding the lamps, flames and eyes reliably (the auto-mask and a brightness search both miss), and the edits' cost: ~2 min per lamp, ~4 min per person's blink.
  4. *True image-to-video* (a 2–4 s loop from the still). mflux has no video models; this needs a separate local runtime and likely takes minutes per clip on a Mac. Out of reach for now.

- **A figure inside its 2.5D scene: SHARP's background with a TripoSplat or LiTo figure.** Tried 2026-10-04 (docs/research/image-to-3d.md, "a figure inside its 2.5D scene"): works, and makes a figure look far better than alone on black, though the person becomes the figure's redrawing at the picture's own view. - **TypeScript 7 for the web app** (noted 2026-10-21, Mac; parked the same day). The web is type-checked by vue-tsc 3.3, which patches TypeScript's JavaScript compiler; TypeScript 7.0.2 (the Go rewrite) no longer ships it (`lib/tsc`), so vue-tsc fails at start (vuejs/language-tools #6124 and #6156, closed in favour of #5381), and Microsoft's TypeScript 7 announcement says Vue workflows can't use 7 yet, for want of a stable programmatic API. Two ways on: [typescript-native-bridge](https://github.com/johnsoncodehk/typescript-native-bridge), the Vue tools maintainer's fork of the `typescript` package with tsgo underneath, swapped in by a package override (the Vue tools repo checks itself with it, ~2.7× faster; untried here, nor whether Deno's npm support takes the override); or TypeScript 7.1's content mappers, which let `tsc` check `.vue` files itself (microsoft/typescript-go #4712, merged 2026-08-19). 7.1 is in beta (2026-10-20, content mappers and a new programmatic API included, both still being refined), with a release candidate due in about a month and the final release shortly after. Vue's side is Vue Language Tools v4 (vuejs/language-tools #6170, an open alpha on 2026-10-21): `tsc --runExternalCode` with `@vue/content-mapper` under `contentMappers` in `tsconfig.json` replaces `vue-tsc`, and that package isn't on npm yet. Here the whole check takes ~2 s, so the bridge would save about a second for a third-party fork: not worth it. Trigger: TypeScript 7.1 final and a released Vue Language Tools v4; then move the web's check to `tsc` with the content mapper and drop vue-tsc. The server's `deno check` is Deno's own TypeScript and isn't affected.
