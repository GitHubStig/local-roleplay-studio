# Open threads

Ideas deliberately deferred. Promote an item to an ADR in `docs/adr/` when we act on it.

- **Persistent image sidecar.** Replace per-Frame `mflux-generate-*` CLI calls with a small Python service that keeps the Image Model loaded and exposes `POST /generate`. Trigger: model load time dominates Frame latency. Measured 2026-09-24: loading is ~5 s of a 42 s Z-Image Turbo render and FLUX.2 Klein 4B renders in ~13 s total, so the gain is small for now. Slots in behind `ImageGenerator`.
- **Edit-based rendering for Subject consistency.** Render each Frame by editing the previous image (`mflux-generate-kontext`, `mflux-generate-qwen-edit`, `mflux-generate-flux2-edit`) instead of generating from scratch. Trigger: the fixed Subject description plus a fixed seed still lets the Subject drift between Frames. Slots in behind `ImageGenerator`.
- **Starring Frames.** Let the player mark favourite Frames for a contact-sheet export. Not a new concept; a flag on a Frame.
- **Narration that doesn't match the Image Prompt.** The Narration is the Text Model's own list of what changed, so a small model can list a change it didn't make, or miss one it did. The Prompt tab's word diff comes from comparing the paragraphs, so it's always right. Seen with spark-x2.5 4B: the Narration claimed "Expression: scared" while the prompt still said she was smiling. Larger Text Models (gemma4 31B, qwen3.8 27B) apply compound Actions fully. Option: check the Narration against the diff, or build it from the diff.
- **Idle animation between Frames.** Keep the image alive while the player is thinking: flickering candles, drifting haze, the Subject blinking or shifting her weight, with the Image Prompt itself unchanged. Idle work must never block a Frame: it runs only after a commit, and is cancelled the moment the player sends an Action, since it competes for the same GPU and memory. Options, cheapest first:
  1. *Browser-only effects.* A slow pan and zoom over the still, plus ambient overlays picked from Image Prompt keywords (haze gives drifting fog, candles give a warm flicker, a rim light gives a soft pulse). Instant, and no extra rendering. Effects can't know *where* the candles are, so they stay generic.
  2. *Subject mask plus layered effects.* Cut the Subject out of the finished image with a background-removal model (mflux lists `fibo-edit-rmbg`; not downloaded yet, unverified), then animate only the background layer (fog, flicker, slight parallax) behind her. Better than rendering the background and Subject separately and compositing: separate renders don't share lighting, shadows or perspective, so the Subject looks pasted on.
  3. *Idle variant frames via image editing.* After commit, edit the Frame's image into a few near-identical frames ("eyes closed", "weight on the other foot", "candle flames taller") and crossfade or flash between them; a 150 ms eyes-closed frame every few seconds reads as a blink. Instruction-based editors in mflux 0.20: `mflux-generate-flux2-edit` (FLUX.2 Klein; weights already cached, likely ~15 s per frame), `mflux-generate-qwen-edit` (Qwen Image Edit, ~20B, not downloaded, much slower), `mflux-generate-kontext`, and `mflux-generate-fibo-edit`, which takes a `--mask-path` to edit only the background. The engine, not the player, writes these edit instructions, from a fixed list, so they stay within the Shoot Brief.
  4. *True image-to-video* (a 2–4 s loop from the still). mflux has no video models; this needs a separate local runtime and likely takes minutes per clip on a Mac. Out of reach for now.
- **Configurable image transitions.** Frame images currently crossfade over 700 ms (on purpose, even when the system asks for reduced motion). Add a Settings option for the transition style (crossfade, fade through black, slide, a slow zoom in, a "flash" like a camera shutter, none) and its duration. It's a display preference, so it belongs per browser like the theme, not in `settings.json`.
  - *While rendering* is a separate choice from the swap itself, so a toggle of its own: leave the current image as is; **blur and dim it** (about 6–8 px plus slight darkening) until the new image is ready, then sharpen into it; or **show the image forming**, using mflux's `--stepwise-image-output-dir` (flagged experimental; decodes every step, so it adds render time; unmeasured) to stream each denoising step, so the picture visibly resolves from noise. On Cancel or failure the current image must return to sharp.
- **Forking from an older Frame.** Picking a Frame in the Frames list only changes what's shown (a "Viewing Frame 1 of 4 · Back to latest" pill says so); the next Action always continues from the latest Frame. To explore "what if" from an earlier Frame:
  1. *Continue from this Frame* (medium): a button on an older Frame starts a new Session with Frames 0 to N copied (same Scenario, seed and settings) and carries on there. The original Session is untouched, and each Session stays a simple line, so the Frame engine and ADRs 0001/0003 don't change. Copies need fresh image file names.
  2. *Branches inside one Session* (large): the Frames list becomes a tree. Changes the data model, the Frames list UI and storage; only worth it if branching becomes central to play.
- **Editing the Image Prompt by hand.** Let the player edit the paragraph directly in the Prompt tab and re-render, as a Frame with no Action (or with "edited by hand" as its Action). The engine's Limits check applies as usual.
- **The Art Agent: rendering a Roleplay.** Picturing and rendering are built: **Picture this** writes a Frame's Image Prompt (a Look written once from the Cast, plus seven sentences from the story up to the Frame; see design.md) and shows it, unrendered. Next:
  1. *Automatic.* Optionally picture and render each new Reply in the background, cancelled when the player sends a Message.
  2. *Prompt length.* Pictures run to about 250 words; check what each Image Model actually reads before trimming further.
- **Long Roleplays.** Every call sends the whole conversation. Once a Roleplay nears the Text Model's context (131,072 tokens for gemma4 here), summarise the oldest exchanges into the system message, or drop them. Not needed yet.
- **Scene state in a Roleplay.** Where everyone is, the time, the weather and the Character's mood live only in the history (ADR 0007). If the Character loses track, track them explicitly: a `scene` field in the Reply, or a separate small call after each exchange.
- **Memory headroom on a 48 GB Mac.** Memory runs past 40 GB, and into swap past 48, when two big models are loaded at once; the models' weights are what's big, not the Python running them. Peaks measured: gemma4 31B ~19–21 GB and the heretic 26B-A4B ~16 GB in Ollama; FLUX.2 Klein 4B ~10.5–18 GB, Klein 9B ~21–28 GB, Qwen-Image 2.1 ~20.5 GB at 512 px, Krea 2 ~39 GB, SeedVR2 ~39 GB; Higgs TTS 3 ~10 GB, Qwen3-TTS VoiceDesign ~7 GB. Done: the voice service no longer grows (its MLX cache held 36 GB) and unloads after a minute (it reloads in 2–3 s); Quantize renders from a saved copy (3.5–8 GB less). Left: **unload the Text Model before a render or upscale**: Ollama keeps a model loaded 5 minutes after its last use; the app could unload it first (`keep_alive: 0`) at the cost of reloading it for the next Reply (seconds for the heretic, more for gemma4 31B).
- **ComfyUI as a backend, for Windows with an NVIDIA card.** mflux is Apple Silicon only, so the app as built renders only on a Mac. ComfyUI runs on both, and has a local HTTP and WebSocket API (checked 2026-10-02 against the installed ComfyUI 0.37.4, Comfy Desktop, on `127.0.0.1:8188`):
  - `POST /prompt` queues a workflow (its "Export (API)" JSON) and returns a `prompt_id`;
  - `GET /history/{prompt_id}` or `/api/jobs/{id}` lists its outputs, and `GET /view?filename=…&type=output` fetches one;
  - `POST /upload/image` sends an input picture (for Upscale, edits, a panorama, TripoSplat);
  - the `/ws?clientId=…` WebSocket reports which node is running and step progress;
  - `POST /interrupt` and `/api/jobs/{id}/cancel` cancel, and `POST /free` unloads its models (useful before a voice or a scene, as for the Text Model);
  - `GET /object_info` lists installed nodes, and `/system_stats` GPU memory.

  It would slot in behind `ImageGenerator` as a third generator beside mflux and the placeholder: one workflow template per Image Model (and the upscaler), with the prompt, seed, steps and size filled in, chosen in Settings. Unlike mflux's process per image (ADR 0004), ComfyUI is a long-running server that keeps models loaded: faster renders, but it holds the memory until `/free`. What wouldn't come along on Windows: the voice service (mlx-audio is MLX, Mac only: Higgs TTS 3 and Qwen3-TTS have PyTorch releases that run on CUDA, or a ComfyUI TTS node), SHARP's script (hardcoded to `mps`; it runs on CUDA too, by changing the device), and the saved quantized copies (mflux's format; ComfyUI has its own fp8 and GGUF models). Ollama runs on Windows as is.
- **Hide what's switched off.** With `VOICES=off`, `SCENES=off` or `FIGURES=off` the buttons still show (Listen, Speak replies and the Voice panel; Make 2.5D; Lift figure and the 3D figures section), and pressing one fails at once with the reason ("3D figures are off (FIGURES=off)"). Already-made audio, scenes and figures still play and open. Option: have `/api/settings/options` (or `/api/health`) say which are on, and hide the buttons that would only fail, keeping the viewers for what exists.
- **A figure inside its 2.5D scene: SHARP and TripoSplat together.** Replace the person in a SHARP scene with their TripoSplat figure, so they stay solid as it turns. SHARP's splats sit on a 768×768 grid over the picture (two layers), so a cut-out mask (BiRefNet, which TripoSplat ships) picks the person's splats to drop; the figure is then placed where they were: scaled, turned and moved so that, seen from the picture's camera, it covers their outline, starting from TripoSplat's own camera guess (its sampler predicts one) and SHARP's depth for the person's pixels, then fitted to the mask if that guess is off. Both are standard 3DGS `.ply` in the same axes, so merging is appending one to the other. Expected gain is modest: 2.5D only turns ~30°, so their back is never seen. Risks: a person-shaped hole in what was behind them once it turns (SHARP never saw it; its second layer covers only near edges), the figure's redrawn face or pose not matching the picture, light and brushwork that look pasted in, and people touching each other coming apart. To try: Frame 4 of the Kael tavern (Kael alone), which has both a scene and a figure; a first combined scene is an hour or two if the camera guess is usable, about a day to hold up across several pictures.
