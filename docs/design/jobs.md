# Jobs

Part of the [design](../design.md). Terms in **bold** are defined in [CONTEXT.md](../../CONTEXT.md).

Everything slow beyond a Chain's Frame is a queued job (`server/jobs.ts`, one queue for every Session): pictures, renders, upscales, edits, voices, 3D, clips, the style scores and a Roleplay's music. What every kind of Session does to a Frame's picture is one module (`server/pictureJobs.ts`); each kind's `jobs.ts` adds its own. The player can queue several and carry on with the conversation, the next Action or edits.

- **One job at a time on each machine** ([ADR 0020](../adr/0020-jobs-take-turns-per-machine.md)), across all Sessions, in the order asked: a picture on the Text Model's server, a render on the Session's Image backend, an upscale, an edit or a voice on Settings' backends, 3D and the style scores here. So the Mac and a PC work side by side.
- **A job waits for what it needs**, wherever that runs: a render for its picture, an upscale for its render, 3D for its upscale, a spoken line for a voice being designed. One asked for before what it needs exists fails with a reason if that still isn't there when its turn comes.
- **A picture goes ahead of queued image jobs**, so a new Reply's Image Prompt is written while the Text Model is loaded, not after a batch of renders that each unload it.
- **Text Model calls take turns with heavy jobs** ([ADR 0029](../adr/0029-text-calls-take-turns-with-heavy-jobs.md)): every call (a Reply, the Cast, a plan, Suggest, a clip's prompt, an Image Prompt) waits for the heavy job running on the Text Model's machine, then goes ahead of those waiting, with any other text calls; the next heavy job unloads the Text Model again. **Clips go behind other heavy jobs**, except image work on a clip's own Frame.
- **A render keeps the Image Model it was queued with**, and a clip the Image Model of the picture it's made from, and its video model: the one it was ordered with, else Settings' default as it's queued; a job that asks the Text Model (a picture, music direction, a voice, a spoken line's directions) keeps the Session's Text Model and Thinking ([ADR 0037](../adr/0037-a-session-switches-text-model.md)). So switching mid-queue leaves queued work where it was.
- **Jobs don't hold the Session's lock**: every change to a Session (a Reply, a picture, a render, a Frame, an Undo) is saved by reloading it and applying just that change, one at a time (`server/update.ts`), so none overwrites another.
- **Failed and done jobs stay listed** until dismissed, failed ones with Retry. **Cancel all** cancels what's running and queued, leaving what's finished; **Dismiss finished** dismisses what's done and failed. Undoing a Frame cancels its jobs; deleting the Session cancels all of them.
- **The queue is kept in a file** (`queue.json`, beside Settings, one for the whole app; `server/queueStore.ts`), saved as jobs are queued, start, end or are dismissed. A server restart (an edit under `server/` in development, with `--watch`) puts it back: queued, failed and done jobs as they were, a job that was running queued again in its place to run from the start, and a Session gone meanwhile losing its jobs. While a job runs it records what it leaves on a ComfyUI (`Job.comfy`: its prompt ids and uploads, reported by the ComfyUI client through `server/comfyui/traces.ts`), which it cleans up itself as it ends; one cut off by a restart is cleaned up after at startup (`clearTraces`): its prompt stopped, its outputs blanked from ComfyUI's history, its history entry deleted and its uploads blanked. A clip, which takes minutes, is picked up instead (`Job.resume`, `pickUp` in `server/video/comfyui/comfyui.ts`): run again, it waits for its prompt if ComfyUI still makes it, fetches the clip and saves it as it would have, then cleans up; if ComfyUI lost or failed it, it's made anew. A picture can't be: it comes back only over the WebSocket that died with the server. Streamed text work (a Reply being written) isn't a job, and a restart ends it.
- **The Queue page** (`/queue`, `GET /api/queue`) shows every machine's line across Sessions: what runs, what waits in the order it will go (the Text Model's calls among it, labelled by what they're for), and what's finished, with how long each waited and took (`Job.startedAt`, `endedAt`). A job opens in its Session as that Session's Queue tab opens it (`?job=…&frame=…`, `useJobLink`); a Chain's own Frame step, which isn't a job, isn't listed.
- **A system notification when the queue is done**, if turned on in Settings (Sessions; per browser, as the browser's permission is): once everything queued in a Session has finished, failed or done, while the app's tab is hidden. Titled with the Session, it says how many failed; clicking it brings the tab back. The Session on screen is followed, or every Session while the Queue page is open, as those are the queues the page polls. A page can't flash the taskbar or bounce the Dock (that needs a native shell), and a count in the tab's title or an app badge (which needs a PWA) wasn't wanted, as the Queue tab shows what's running and what failed.
